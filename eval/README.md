# 評価（Phase 2）— 精度を数字で測る

RAGの「なんとなく動く」を「数字で良し悪しが言える」状態にするための土台。

## 何を測るか

RAGの精度は2層に分けて測る。

| 層 | 問い | 指標 |
|---|---|---|
| 検索 Retrieval | 正しい資料を拾えたか | **Recall@k** / **MRR** |
| 生成 Generation | 回答は正確で資料に忠実か | **事実カバー率** / **忠実性** |

- **Recall@k**：上位k件に正解の出どころが入っていた割合（取りこぼさなさ）。
- **MRR**：正解が何番目に出たかの逆数の平均（順位の良さ。1位=1.0, 2位=0.5…）。
- **事実カバー率**：回答が「含むべき事実」をどれだけ含んだか（決定的・API不要の正確さ代理）。
- **忠実性**：回答が渡した資料だけで裏付けられるか（Ragasのfaithfulnessの素朴版・LLM判定）。

## 構成

```
eval/
  corpus/        評価用コーパス（互いに別トピックの小文書10件）
  dataset.json   ゴールデンQ&A（質問→正解の出どころ＋含むべき事実）
  metrics.py     指標の計算（純Python・中身が読める）
  run_eval.py    取り込み→検索→採点を実行
```

ゴールデンの正解は「出どころ(source)」で持つ。チャンクIDは取り込み直すと変わるが、
出どころ名は安定なので、設定を変えて入れ直しても評価がやり直せる。

## 使い方

```bash
# pgvector が起動していること
cd /Users/ayaka/rag-lab

# 検索だけ評価（埋め込みのみ＝無料枠が別で気軽に回せる）
.venv/bin/python -m eval.run_eval

# 生成も評価（回答生成＝LLM呼び出し。1問ごとに待機）
.venv/bin/python -m eval.run_eval --judge

# 忠実性のLLM判定まで（呼び出し倍増）
.venv/bin/python -m eval.run_eval --judge --faithfulness

# チャンク設定などを変えた後、コーパスを入れ直してから評価
.venv/bin/python -m eval.run_eval --reset
```

## 注意：生成は無料枠の上限が小さい

`gemini-2.5-flash` の無料枠は1日あたりのリクエスト数が少ない（20前後）。
`--judge` はそれを消費するので日に何度も回せない。429に当たったら、その時点までで
集計して止まる作りにしてある。**検索評価（埋め込み）はクォータが別**なので普段はこちらを回す。

## いまの結果と読み方

トピックが明確に分かれているため、現状の検索は **Recall@1 = 1.000（満点）**。
「土台が正しく動く」ことの確認としては十分。ここから先、評価が本当に効いてくるのは：

- 質問を言い換え・間接的にして難しくする（検索が外す状況を作る）
- **Phase 3** でチャンク戦略を変え、この数字が上下するのを観察する
- 紛らわしい類似トピックの文書を足して distractor にする

つまりこの土台は「変更の良し悪しを数字で判定する物差し」。Phase3以降で活きる。

---

## Phase 3 — チャンク戦略の実験

分割のやり方（戦略・サイズ）を変えると検索精度がどう変わるかを、上の物差しで測る。

### なぜ専用の長文コーパスが要るか

通常の評価コーパス（`corpus/`）は「1トピック＝1文書＝ほぼ1チャンク」なので、
分割方法を変えても結果が変わらない。そこで Phase3 では全トピックを1つの長い文書に
まとめた `corpus_long/handbook.md` を使う。長い文書なら「答えがどのチャンクに入るか」が
分割で変わり、検索の当たり外れに効いてくる。

### 実行

```bash
.venv/bin/python -m eval.compare_chunking
```

複数の分割設定で handbook を入れ直し、各質問で「上位k件のチャンクに答えの事実が
入っていたか（文脈カバー率）」を k=1/2/4 で測って並べる。検索（埋め込み）のみで
生成の枠は使わない。実験のため一度DBを空にし、終了時に通常コーパスへ自動復元する。

### 測ってわかったこと（例）

```
分割設定          チャンク数  平均文字  カバー@1  カバー@2  カバー@4
fixed   200/40       13      199     0.875    1.000    1.000
fixed   500/100       6      435     0.917    1.000    1.000
fixed  1000/200       3      837     0.917    1.000    1.000
sentence 300          8      261     0.667    0.917    1.000
```

- **k=1（1チャンクだけ使う）で差が出る**。大きめのチャンクは1件に情報が多く入るので
  単独で答えを含みやすい。小さすぎると事実が別チャンクに分かれて取りこぼす。
- **k=4 まで取ると差は消える**（多めに取れば結局カバーできる）。
- ただし大きいチャンクは無駄な文章も一緒に渡る＝LLMへのノイズ増。実運用は
  「精度 ↔ ノイズ」の綱引きで最適サイズを選ぶ。評価があると、この選択を勘でなく
  数字でできる。

### 埋め込みにも上限がある（ハマり）

埋め込み(gemini-embedding-001)は**毎分100回**の無料枠上限がある。バッチで叩くと
429になるため、`_embed` は429を待って自動再試行する。生成(1日)とは別枠・別単位。
